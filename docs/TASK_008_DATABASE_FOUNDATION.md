## Two reproducible migration paths

Run the existing `npm.cmd run db:provision`, `npm.cmd run db:migrate:local`, `npm.cmd run db:check` commands on native Windows PostgreSQL 17. Stop the API during an existing-database upgrade and restart it afterward. No Docker/WSL is needed. Preserve your private environment files and database backup; do not point local scripts at a cloud database.

- **Existing original database:** keep all five historical migrations/history checksums. The new forward migration `20261104000100_stich_auth_namespace.sql` renames the application-owned `auth` schema to `stich_auth`, preserving table OIDs, rows, references and ACLs. It explicitly redefines the 18 reviewed function bodies to reference `stich_auth`, retaining owners, execution ACLs, volatility and fixed `pg_catalog` search paths. PostgreSQL updates the policies' stored object dependencies during the rename. The migration runner checks the legacy security contract before transition, so it cannot overwrite drift and then bless the altered database.
- **Fresh database:** the runner executes the five explicit `database/bootstrap/*.sql` artifacts, which differ from historical sources only by the approved `auth` → `stich_auth` namespace mapping, then the forward migration. It never creates, renames or repairs provider-owned `auth`. `bootstrap-manifest.ts` separately pins original source bytes and executable bootstrap bytes. There is no dynamic SQL text replacement at execution time.

The historical files remain byte-for-byte unchanged. `public.migration_history.checksum` continues to record the original source SHA-256. Two additive provenance columns record `execution_checksum` and `execution_mode` (`original` or `stich_auth_v1`) for new executions. Old records legitimately retain null execution provenance; they are not falsely relabelled as mapped executions. The ledger thus distinguishes original replay from namespace-compatible bootstrap. Both original and executable checksums are verified on repeat runs. Missing/out-of-order migrations and mismatched source/execution checksums fail transactionally. Transaction-level advisory locking serialises runs.

Fresh bootstrap artifacts, source migrations and the manifest must be shipped together. Changing a historical file, mapped artifact or the historical pins is not the process for a future change: add a reviewed forward migration. `.gitattributes` preserves LF SQL bytes across Windows/Linux checkouts.

## Security contract

Application SQL routes, tenant context and test fixtures use `stich_auth`. Business tables stay in `public`. The private schema has no PUBLIC access; sensitive tables have no runtime SELECT grants. The runtime remains NOSUPERUSER/NOBYPASSRLS/NOINHERIT/NOCREATEROLE/NOCREATEDB/NOREPLICATION. It cannot assume the migrator. The 18 SECURITY DEFINER functions keep their restricted owner and explicit execution allowlist. FORCE RLS, exact policy bodies, function hashes and ACL grantor identities remain checked. Owner/cashier, shop/branch, session revocation, password reset and cost-price restrictions retain their logic.

`legacy-security.ts` and `legacy-security-manifest.ts` freeze the original contract for pre-transition provisioning/upgrade validation only. API readiness uses the new namespace contract, never the legacy fallback.

`validateSecurity(..., managedContract)` provides a **test/tool-only** explicit managed catalogue comparison. A contract supplies reviewed database identity/ACL, public-schema owner/ACL, and provider schema owners. It must never be generated by trusting the same live snapshot under validation. Provider namespaces are allowed only under those explicit owners. Unknown schemas/ownership fail. Application table/function/policy/ACL checks remain exact, including in `public`; provider objects in `public` are not broadly exempted. Unexpected application role memberships in either direction are rejected, preventing indirect privilege inheritance and SET ROLE paths.

Cross-boundary checks reject application ownership or grants in provider namespaces, PUBLIC table/sequence exposure, column grants, accessible provider functions, privileged parameter grants and unexpected application types. Local mode still rejects provider schemas, so selecting the managed contract is explicit and cannot silently relax a normal local readiness check. Database CREATE and public-schema CREATE cannot be granted to the runtime via a permissive managed contract.

The reviewed contract is not yet wired into remote API configuration. It does not assert that a Supabase customer can perform all required grants, alter public-schema ownership, remove relevant provider defaults or satisfy zero application-role memberships. Those behaviors require the approved dedicated managed-project test. Managed owner/role and Data API exposure settings must be reviewed before enabling remote operation. A service-role key is not a substitute for restricted database credentials.
